# TEP-003: TDF Specification 0.6.0 Exploratory Design and Conformance Roadmap

> [!NOTE]
> **Planned Specification Document (`status: planned`):** This TEP defines the complete, normative specification changes for **TDF `0.6.0`** based on operational feedback from `0.5.0` / `0.5.1` workflows and multi-tool/agent interoperability. The focus of this proposal is exclusively on [`TDF_SPEC.md`](../../TDF_SPEC.md) semantics, concurrency rules, schema evolution, and machine-readable conformance fixtures — not on modifying the application source code in this step.

## Part 1: Concept & Proposal

### 1.1 Summary
This proposal defines the specification roadmap for **TierTask Data Format (`TDF`) `0.6.0`**. It organizes the specification into a **Mandatory Core Scope for `0.6.0`** (Topics 1 through 10 and Topic 12) and a **Deferred Scope** (Topic 11), structured into nine specification capability areas across Topics 1 through 12:
1. **Guarded Local Publication, Bounded CAS-Merge Loop (`MAX_CAS_RETRIES`), and Canonical Root-Block Sorting (Topic 1):** Normative SHA-256 `sourceDigest` verification before save using loop-local retry state (`loopDigest`, `loopB`, `loopL` committed only after atomic rename succeeds), automatic three-way reload-and-merge on mismatch, CSPRNG dot-prefixed `O_CREAT | O_EXCL` (`0600`) temp-file swap with unconditional error `unlink` and no sync-folder `.tdf.lock` ghost files, and deterministic ASCII-ID sorting of `label`, `location`, and `task` root blocks so identical merged states yield byte-identical `.tdf` files.
2. **Non-Blocking Target Deadlines (`due`) Coupled with Schedule-Anchored Recurrence and Local Calendar Lead-Time Preservation (Topics 2 & 9):** A non-blocking `due <timestamp>` directive (pure deadline metadata at canonical `task` position 11 with no `suspended <= due` parse constraint, merged as an independent scalar within the same occurrence) that acts as a fixed calendar anchor when combined with `repeat`, advancing `due` by the smallest multiple $k \ge 1$ of `<count> <unit>` in local calendar space until `newDue > now` and advancing `suspended` (`oldSuspended < oldDue`) by the same $k \times \text{<count> <unit>}$ in local calendar space — adjusting `candidateSuspended`'s local day to $\max(1, D_{\text{end}} - (D_d - D_s))$ whenever $(Y_s, M_s) = (Y_d, M_d)$ with $D_s < D_d$ and advancing both by $k \times \text{<count> months}$ places both on the target month's last valid day $D'_s = D'_d = D_{\text{end}}$ (i.e., $D_s \ge D_{\text{end}}$ and $D_d > D_{\text{end}}$, such as `Jan 28` or `Jan 29` with `Jan 31` -> `Feb 25` or `Feb 26` with `Feb 28`), or defaulting `suspended` to the start of the `newDue` local day when `suspended` was omitted, `forever`, or $\ge \text{oldDue}$ — so neither DST transitions nor month-end clamping shift local wake-up times or collapse the preparation window.
3. **Dedicated Machine Correlation Keys (`origin "<namespace>" "<external-key>"`) and Executable URI Scheme Prohibition (Topic 3):** Preserving `link "<title>" "<uri>"` (`0..20`) strictly for user-facing clickable links, rejecting executable URI schemes (`javascript:`, `vbscript:`, `data:`) with `InvalidUri`, and introducing an optional single-valued passive correlation directive `origin "<namespace>" "<external-key>"` (`0..1` per `task`, without enforcing document-wide uniqueness across distinct `task` blocks in the parser so concurrent offline imports merge cleanly, canonical position 12 between `due` and `link`, `1..MAX_TEXT_LENGTH` single-line `<text>` arguments, placed in `Task payload` as `(created, name, note, labels, condition, origin, link, Task state)`, merged as one atomic `(namespace, externalKey)` scalar pair, preserved across completion, recurrence, and restoration, and redacted in diagnostic logs) so external CLI tools, scripts, and AI agents can deterministically identify and deduplicate imported tasks even after users edit `name`, `note`, or `link`.
4. **Executable Conformance Suite and Historical Unicode Scalar-Value Clarification (Topic 4):** Versioned `.tdf` and `.json` test vectors under `spec/conformance/` and an explicit rule in Section 10.1.1 that all historical schemas (`0.2.0`–`0.5.1`) measure character limits in decoded Unicode scalar values.
5. **Elevating Concurrent Entity References (`labels` and `condition location`) and Direct Edits Targeting Deleted Entities to `DeletionConflict` (Topic 5):** Prohibiting silent removal of newly added `labels` references or `condition location` references (both `X minus B` on existing entities and all references on newly created entities absent from `B`, evaluated across all live and `DeletionConflict`-retained entities before `condition` winner selection or deletion cascades) when the target `label` or `location` appears in opposing `deleted`, preserving the live `label` or `location` block and classifying both direct payload edits and newly added references normatively as `DeletionConflict` (Section 6.8.2) so `Delete` vs. `Undelete` resolves them cleanly.
6. **View-Scoped Labels (`label <label-id> [scoped] {`), Global-View Flood Protection, and Context-Relative Downgrades (Topic 6):** Restricting tasks to explicit label views and search when all assigned labels carry `scoped`, ignoring `scoped` labels during global-view condition evaluation of mixed-label tasks, automatically unscheduling (`queue` removal to `Someday` while preserving `suspended`) tasks that lose their last label due to a `scoped` label deletion (across explicit deletes, conflict resolutions, and three-way merges), and evaluating the `Focus -> Ready` downgrade anchor (Section 6.3) strictly against the Section 5.5 priority-partitioned executable sequence $E_{\text{ctx}}$ of the active filter context.
7. **Same-Occurrence Merge Unbundling, Key-Value Map Merge for `blocked`, Step-Wise `subtasks` Merge, Pre-Merge Tombstone Stripping on `condition`, and Independent `scoped` Flag Merge (Topics 6, 7 & 8):** Merging the `label` `scoped` flag as an independent boolean scalar, stripping non-conflicting tombstoned `<location-id>` tokens from `B.condition`, `L.condition`, and `R.condition` (removing an emptied `location` rule and projecting a task's cascade-inserted `location any` back to the empty `locationGroup` when `B.locationGroup` contained only locations tombstoned on that side) before three-way `condition` comparison and merging `condition` per rule group (`dayGroup`, `timeGroup`, `locationGroup`) with commutative `W`-anchored `<location-id>` ordered-list merging, unbundling `priority`, `suspended`, `due`, `repeat`, `blocked`, and `subtasks` when `B.completions == L.completions == R.completions` and `finished` is omitted in all three, merging `blocked` as a `(targetId -> requiredCompletion)` map per `targetId`, and merging `subtasks` boolean steps individually when the ordered step text sequence matches across `B`, `L`, and `R`.
8. **First-Class Reusable `location <location-id> { ... }` Entities and ID-Referenced `condition location` Rules (Topic 12):** Promoting geofence locations to first-class root blocks (`location <location-id> { ... }`, bounded by `MAX_LOCATIONS = 200`) with `name`, optional `note`, passive `source` (no automatic network geocoding), 6-decimal `coordinates <lat> <lon>` coupled with `source` as an atomic geographic merge unit, `radius <meters>` ($\le \text{MAX\_LOCATION\_RADIUS} = 100\,000$), and `modified` (defaulting to `1970-01-01 00:00:00` UTC when omitted), while `condition` `location <loc-1> [<loc-2> ...]` rules coalesce per entity (capped at `MAX_LOCATION_REFS_PER_ENTITY = 63` `<location-id>` tokens so coalesced inline and block forms never exceed `MAX_ARGS_PER_STMT = 64`), cascading deletion strips non-conflicting tombstoned `<location-id>` tokens before `condition` comparison and updates `label` blocks before `task` blocks (rewriting an emptied task `location` override to `location any` when an assigned live label defines a non-empty post-cascade `location` rule), and `0.5.1 -> 0.6.0` migration deterministically rounds legacy high-precision `0.5.1` coordinates/radii using `half-away-from-zero` to 6 / 2 decimal places (failing with `InvalidNumber` if the rounded radius equals `0`) and extracts inline coordinate triples into root `location` blocks named `"Location (<normalizedLat>, <normalizedLon>, <normalizedRadius>m)"` while the native `0.6.0` parser strictly rejects $> 6$ / $> 2$ non-zero fractional digits with `InvalidNumber`.
9. **Prerequisite Expiry Hygiene on 30-Day Tombstone Retirement and Time Zone Context Separation (Topics 10 & 11):** Prohibiting automatic pruning of missing prerequisite IDs during parsing, loading, or ordinary mutations (preserving forward references) while deterministically removing `blocked <id>[:<req>]` references when a confirmed `task <id>` deletion record expires from `deleted` after $> 30$ days (Section 6.8.3), and keeping time zone context out of entity blocks.

### 1.2 Motivation
`TDF_SPEC.md` `0.5.0` and `0.5.1` established a deterministic, single-pass $O(N)$ grammar with dynamic 6-tier derivation (`Focus`, `Ready`, `Planned`, `Blocked`, `Someday`, `Completed`), monotonic entity revisions, shared `queue` and `deleted` blocks, completion occurrence counters, and three-way baseline synchronization. Practical multi-actor operation across the TierTask GUI, autonomous CLI/AI agents, and cloud file synchronizers (OneDrive, Nextcloud, Syncthing) motivates targeted specification refinements for `0.6.0`:

1. **Unguarded Local Overwrites and Non-Deterministic Block Order:** Without a mandatory SHA-256 `sourceDigest` check and reload-and-merge loop before local writes, a long-running application session can overwrite external agent edits or cloud-sync atomic file replacements. Furthermore, because `0.5.1` leaves root entity block order dependent on declaration order, two clients merging the same state can emit byte-different files with different SHA-256 digests.
2. **Deadlines vs. Availability and Schedule Drift on Recurring Deadlines:** `suspended` blocks a task in `Tier 4` until its start instant arrives, whereas a deadline (`due`) must leave an actionable task in the active pull cycle (`Tier 1–3`) today. Moreover, recurring tasks with fixed calendar deadlines (such as monthly billing on the 15th with a preparation window starting on the 10th, or end-of-month tasks on Jan 31 with a preparation window starting on Jan 29) drift or lose their multi-day lead window across shorter months if `repeat` only calculates from completion time (`localNow`) or clamps `suspended` and `due` to the same month-end day without adjusting `candidateSuspended`'s day to $\max(1, D_{\text{end}} - (D_d - D_s))$.
3. **User-Facing Links vs. Agent Deduplication Keys:** Overloading `link "<title>" "<uri>"` with a third synchronization parameter would couple internal agent deduplication to visible UI links that users freely edit or delete, whereas a dedicated `origin "<namespace>" "<external-key>"` (`0..1`) directive isolates immutable external correlation identifiers from user-facing `link` items.
4. **Cross-Language Conformance and Historical Length Units:** Prose verification tables in `TDF_SPEC.md` cannot be executed automatically by independent parsers, and historical schema snapshots (`0.2.0`–`0.4.0`) lacked an explicit statement that character bounds count decoded Unicode scalar values rather than UTF-16 code units or UTF-8 bytes.
5. **Silent Loss vs. Actionable Resolution on Deleted Label or Location References:** A concurrent local assignment of a `label` or `location` that was deleted remotely must neither vanish silently nor halt with an unrecoverable schema syntax error when the existing `DeletionConflict` (`Delete` vs. `Undelete`) workflow in Section 6.8.2 can resolve it directly.
6. **Dedicated Context Lists (`scoped` Labels) and Post-Deletion Queue Flooding:** Users need opt-in `scoped` labels whose tasks appear only when that label filter is selected (or in search). At the same time, deleting a `scoped` label (e.g., a 25-item vacation packing list in `queue`, whether locally, via conflict resolution, or during three-way merge) must not strip the label and suddenly dump 25 unlabeled tasks into the global `Focus` and `Ready` tiers.
7. **Coarse Same-Occurrence and Monolithic `condition` Merge Granularity:** Copying the entire occurrence state atomically when `completions` and `finished` are unchanged discards non-conflicting concurrent edits to `priority`, `suspended`, `due`, different `blocked` target IDs, or different `subtasks` steps; likewise, comparing `condition` without first stripping non-conflicting tombstoned `<location-id>` tokens causes a remote location deletion cascade to conflict with a local `day` or `time` edit.
8. **Opaque Inline GPS Coordinates Without Reusable Place Metadata (Topic 12):** In `0.5.1`, `location <lat> <lon> <radius>` embeds raw decimal coordinates directly inside `condition` rules without a human-readable title (`name`), description (`note`), or navigable address/location code (`source`, such as a street address, Google Plus Code / Open Location Code, or What3words), and forces users to duplicate raw coordinate triples across multiple tasks and labels. Promoting `location` to a first-class root block (`location <location-id> { ... }`) alongside `label` keeps deterministic offline Haversine evaluation via `coordinates <lat> <lon>` and `radius <meters>` while centralizing place metadata and enabling ID-based `condition location <loc-1> [<loc-2> ...]` references.
9. **Forward Prerequisite References vs. Retired Tombstones and Entity Compactness:** Stripping unknown `blocked` IDs on load or save would break hand-edited forward references, whereas retiring any `blocked <id>[:<req>]` prerequisite reference when `task <id>`'s 30-day deletion record expires is safe and deterministic; likewise, time zone configuration belongs at the operation or workspace level rather than inside every task block.

### 1.3 Prioritization & Scope Partitioning for `0.6.0`
To keep `TDF 0.6.0` focused and protect the single-pass $O(N)$ grammar:
* **Mandatory Core for `0.6.0` (Topics 1, 2 [with Topic 9 integrated], 3, 4, 5, 6, 7, 8, 10, 12):**
  * **Topic 1:** SHA-256 `sourceDigest` CAS-merge loop (`MAX_CAS_RETRIES = 3`, using loop-local retry state `loopDigest`, `loopB`, `loopL` committed only after atomic rename succeeds), CSPRNG dot-prefixed `O_CREAT | O_EXCL` (`0600`) temp-file swap with error `unlink` (no `.tdf.lock` inside synced folders), and canonical ASCII-ID sorting of `label`, `location`, and `task` root blocks.
  * **Topic 2 (integrating Topic 9):** Non-blocking `due <timestamp>` directive (canonical `task` position 11) coupled with schedule-anchored recurrence and DST- and month-end-safe local calendar lead-time preservation (adjusting `candidateSuspended`'s day to $\max(1, D_{\text{end}} - (D_d - D_s))$ whenever $(Y_s, M_s) = (Y_d, M_d)$ with $D_s < D_d$ and advancing both by $k \times \text{<count> months}$ places both on the target month's last valid day $D'_s = D'_d = D_{\text{end}}$).
  * **Topic 3:** Dedicated passive machine correlation directive `origin "<namespace>" "<external-key>"` (`0..1` per `task`, non-unique across distinct `task` blocks, canonical `task` position 12 between `due` and `link`, `1..MAX_TEXT_LENGTH` single-line `<text>` arguments accepting equivalent double- or single-quoted string syntax in input and emitted double-quoted canonically, placed in `Task payload` as `(created, name, note, labels, condition, origin, link, Task state)`, merged as one atomic `(namespace, externalKey)` scalar pair, preserved across completion, recurrence, and restoration, and redacted in diagnostic logs) paired with strict separation from user-facing `link "<title>" "<uri>"` and deterministic `InvalidUri` rejection of executable URI schemes (`javascript:`, `vbscript:`, `data:`).
  * **Topic 4:** Machine-readable conformance suite (`spec/conformance/`) and historical Unicode scalar-value clarification in Section 10.1.1.
  * **Topic 5:** Normative classification of direct payload edits and concurrent `labels` or `condition location` references targeting deleted `label` or `location` entities (on both existing and newly created tasks/labels, across all live and `DeletionConflict`-retained entities before `condition` winner selection or deletion cascades) as `DeletionConflict` (Section 6.8.2).
  * **Topic 6:** View-scoped labels (`label <label-id> [scoped] {`), global-view flood protection on `scoped` label deletion across explicit deletes, conflict resolutions, and three-way merges (Sections 6.7.8, 6.8.1 & 6.8.2), and active-filter-relative step-down downgrade anchors computed against the Section 5.5 priority-partitioned executable sequence $E_{\text{ctx}}$ (Section 6.3).
  * **Topics 7 & 8:** Independent boolean scalar merge for `label` `scoped`, pre-merge stripping of non-conflicting tombstoned `<location-id>` tokens from `B.condition`, `L.condition`, and `R.condition` (removing an emptied `location` rule and projecting a task's cascade-inserted `location any` back to the empty `locationGroup` when `B.locationGroup` contained only locations tombstoned on that side) and group-wise `condition` merge (`dayGroup`, `timeGroup`, `locationGroup`) with commutative `W`-anchored `<location-id>` ordered-list merging, same-occurrence three-way merge unbundling, key-value map merge for `blocked` (`targetId -> requiredCompletion`), and step-wise boolean merge for `subtasks` on matching step text lists.
  * **Topic 10:** Strict preservation of missing `blocked` target IDs during parsing, loading, and ordinary mutations (protecting forward references), paired with deterministic removal of `blocked <id>[:<req>]` references when a confirmed `task <id>` deletion record expires after $> 30$ days (Section 6.8.3).
  * **Topic 12:** First-class root `location <location-id> { ... }` blocks (`name`, `note`, passive `source`, 6-decimal `coordinates <lat> <lon>`, bounded `radius <meters>`, `modified` defaulting to `1970-01-01 00:00:00` UTC, `MAX_LOCATIONS = 200`), coalesced ID-referenced `condition` `location <loc-1> [<loc-2> ...]` rules (`UnknownLocationReference`, `MAX_LOCATION_REFS_PER_ENTITY = 63`), coupled `(coordinates, source)` merging, `location` `deleted` records with pre-merge tombstone stripping on `condition` and label-before-task deletion cascade (`location any` task override preservation), and deterministic `0.5.1 -> 0.6.0` inline coordinate extraction (with `half-away-from-zero` rounding to 6 / 2 decimal places before deduplication exclusively during `0.5.1 -> 0.6.0` migration, failing with `InvalidNumber` if the rounded radius equals `0`).
* **Restrained / Deferred Scope (Topic 11):**
  * **Topic 11:** Keep time zone hints out of entity blocks; defer or restrict to a minimal optional root directive if needed by headless tools.

### 1.4 Detailed Specification Design for TDF 0.6.0

#### 1.4.1 Topic 1: Guarded Local Publication, Bounded CAS-Merge Loop, and Canonical Root-Block Sorting
* **Normative Source Fingerprint (`sourceDigest` — Sections 6.7.2 & 6.7.7):**
  * Bind every loaded working copy and acknowledged baseline `B` to the exact byte length and SHA-256 digest (`sourceDigest`) of the raw `.tdf` byte stream (paired with HTTP `ETag` when synchronizing via WebDAV). Do not rely on filesystem `mtime` or inode numbers alone.
* **Pre-Write Compare-and-Swap (CAS) Merge Loop (`MAX_CAS_RETRIES = 3`) & Hardened Temp-File Swap:**
  * Before persisting a mutated or merged candidate `L` to a local `.tdf` path, initialize loop-local working state `loopDigest = sourceDigest`, `loopB = B` (`absent` if `<target>` did not exist when `L` was initialized), and `loopL = L`, and execute a bounded loop with `attempt = 0..MAX_CAS_RETRIES`:
    1. Read the current byte stream `R_bytes` from the target path (resolving the path afresh on every attempt so atomic file replacements by OneDrive, Nextcloud, or Syncthing are always observed) and compute `diskDigest = SHA256(R_bytes)` (or `diskDigest = absent` if `<target>` does not exist).
    2. If `diskDigest == loopDigest` (including when both are `absent` on initial file creation), serialize the candidate `loopL` into `out_bytes` and validate canonical output bounds (Section 7.1). Create a dot-prefixed temporary file `.<target_basename>.tmp.<csprng_hex>` in the same directory using a $\ge 128$-bit (32-hex-char) cryptographically secure random suffix (CSPRNG), **exclusive creation flags** (`O_CREAT | O_EXCL | O_WRONLY` on POSIX, `CREATE_NEW` on Windows, never following existing symlinks), and restrictive owner-only file permissions (`0600` on POSIX). Write `out_bytes`, flush (`fsync`), atomically rename over `<target>`, and **only after the rename succeeds** commit `sourceDigest = SHA256(out_bytes)`, set durable baseline `B = loopL`, and return success. If writing, flushing, or atomic rename fails (e.g., due to a transient Windows `ERROR_SHARING_VIOLATION` lock), unconditionally delete (`unlink`) `.<target_basename>.tmp.<csprng_hex>` before propagating the failure (leaving the pre-loop `sourceDigest`, `B`, and `L` untouched) so orphaned temporary files are never uploaded by cloud synchronizers.
    3. If `diskDigest != loopDigest` and `attempt < MAX_CAS_RETRIES`:
       - Parse `R_bytes` as incoming document `R` (if `<target>` was deleted externally while `loopDigest` was present, treat `<target>` absence according to Section 6.8.4 recovery rules).
       - Execute the full reconciliation `M = merge(loopB, loopL, R)` (`loopB` = last acknowledged baseline for this loop iteration, `loopL` = current loop candidate, `R` = current disk document; if `loopB` is `absent` because `<target>` was created externally after initialization, reconcile without a common baseline under Sections 6.7.8 and 6.8.4) under Sections 6.7 through 6.11 and validate `M`.
       - **Update Loop-Local State Before Retry:** Set `loopDigest = diskDigest`, `loopB = R`, and `loopL = M`, increment `attempt`, and repeat from Step 1 without mutating the caller's durable `sourceDigest` or `B`.
    4. If contention persists after `MAX_CAS_RETRIES` attempts (`attempt == MAX_CAS_RETRIES` and `diskDigest != loopDigest`), or if parsing/reconciliation yields `DeletionConflict`, `RecoveryRequired`, `SyncGenerationRollback`, or a schema validation error, abort the write without modifying `<target>`, preserve the caller's pre-loop `sourceDigest`, `B`, and `L` unchanged, and report the outcome to the caller.
* **Prohibition of Sync-Folder `.tdf.lock` Artifacts:**
  * Conforming implementations MUST NOT create persistent or advisory `.tdf.lock` files inside the workspace directory, because cloud sync daemons (OneDrive, Nextcloud, Syncthing) replicate lock files across devices and create stale ghost locks. Any optional local inter-process lock MUST use OS-native file-descriptor advisory locking or reside in the local OS runtime temporary directory outside the synchronized folder.
* **Canonical Root-Block Ordering for Deterministic `sourceDigest` Checksums (Section 7.1):**
  * In `0.6.0`, a canonical serializer MUST emit root elements in this exact deterministic order:
    1. `tdf 0.6.0` version header.
    2. `deleted { ... }` block (when present; omitted only when `generation == 0` and zero records exist, with `generation` first, followed by `task` records, `label` records, and `location` records each sorted in ascending ASCII ID order).
    3. `queue { ... }` block (when present; omitted only when `queue.modified` is epoch and zero entries exist).
    4. All `label` blocks sorted in ascending ASCII order of `<label-id>`.
    5. All `location` blocks sorted in ascending ASCII order of `<location-id>`.
    6. All `task` blocks sorted in ascending ASCII order of `<task-id>`.
  * Because active pull-cycle order is stored entirely in `queue` (Section 4.6, formerly 4.5), sorting `label`, `location`, and `task` root blocks by ASCII ID never alters tier derivation or queue order, and guarantees that two independent clients merging the same state produce **byte-for-byte identical `.tdf` output and identical `sourceDigest` hashes**.
* **Verification Cases:**
  * Client A loads at $T_0$; Agent B modifies the file at $T_1$; Client A saves at $T_2$ -> Client A detects `diskDigest != loopDigest`, merges `loopL` and `R` against `loopB`, updates `loopDigest = diskDigest`, `loopB = R`, and `loopL = M`, and commits `sourceDigest` and `B` only after the atomic rename succeeds on the next loop iteration.
  * OneDrive replaces the file via temp-file rename at $T_1$ -> Client A's path-based pre-write check detects the new content digest and reconciles.
  * Client A and Client B perform the same three-way merge in opposite input orders (`merge(B, L, R)` vs. `merge(B, R, L)`) -> canonical serialization produces the exact same byte sequence and SHA-256 `sourceDigest`.

#### 1.4.2 Topic 2 (with Topic 9 Integrated): Non-Blocking Deadlines (`due`) and Schedule-Anchored Recurrence with Local Calendar Lead-Time Preservation
* **Directive Syntax, Canonical Position & Domain Rules (Sections 3.3, 4.1.2 & 7.1):**
  * Add optional single-valued directive `due <YYYY-MM-DD> [<HH:MM[:SS]>]` (`0..1`, listed in Section 3.3 so duplicate declarations produce `DuplicateDirective`) to `task` blocks, stored in UTC and converted from local calendar input under Section 6.10.
  * **Canonical Position & Formatting:** Emit `due YYYY-MM-DD HH:MM:SS` in UTC at **canonical position 11** inside `task` blocks (immediately after `suspended` at position 10 and immediately before `origin` at position 12, in the standardized 15-position `task` directive list of Sections 4.1.2 and 7.1: `1. name, 2. note, 3. created, 4. finished, 5. modified, 6. completions, 7. repeat, 8. labels, 9. blocked, 10. suspended, 11. due, 12. origin, 13. link, 14. condition, 15. subtasks`).
  * **No `suspended <= due` Schema Constraint:** Do not enforce an ordering constraint between `suspended` and `due`. Manually deferring (`suspended`) an already-overdue task to tomorrow while keeping its original `due` date from last Friday is valid and must never fail parsing or validation.
* **Non-Blocking Tier Semantics (Section 5):**
  * `due` NEVER places a task into `Blocked` (`Tier 4`) and NEVER implicitly overrides `queue` order or `priority` in Section 5.5. `queue` membership and `priority` remain the sole determinants of `Focus`, `Ready`, and `Planned` slots; `due` serves as pure deadline metadata for UI display, filtering, and recurrence anchoring.
* **Ordinary Mutation Semantics (`Setting due` — Section 6.6):**
  * Setting or updating `due` converts local calendar input to UTC under Section 6.10, advances `task.modified` once, and **preserves `queue` membership and order unchanged** (unlike `suspended`, setting `due` on an unscheduled `Someday` task does not append the task to `queue`). Clearing `due` removes the directive, advances `task.modified` once, and preserves `queue` membership and order.
* **Coupled Recurrence Anchoring (`repeat` + `due` + `suspended` — Sections 6.4 & 6.10.3):**
  When completing a recurring task (`repeat <count> <days|weeks|months> [<repeat-time>]`):
  1. **Without `due` (`due` Omitted — Completion-Relative Mode):**
     - Exact `0.5.1` behavior: compute `<next_due>` from the completion instant `localNow` + `<count> <unit>` combined with `<repeat-time>` (defaulting to `00:00:00` local time) under Section 6.10.3, require `<next_due> > now`, and store that UTC instant in `suspended` (while preserving `origin` unchanged).
  2. **With `due` Present (`due` as Fixed Calendar Anchor + DST- and Month-End-Safe Local Calendar Lead Window):**
     - **Step A (Advance `due` Along Fixed Local Schedule):** Convert `oldDue` (UTC) into local calendar components $(Y_d, M_d, D_d, h_d, m_d, s_d)$ in the configured IANA time zone. Find the smallest integer multiple $k \ge 1$ such that advancing $(Y_d, M_d, D_d)$ by $k \times \text{<count> <unit>}$ (applying month-end clamping from Section 6.10.3 Step 4 against $D_d$, preserving `oldDue`'s local wall-clock time $(h_d, m_d, s_d)$, and resolving local-to-UTC via Section 6.10.2) produces a UTC instant `newDue > now` with local calendar date $(Y'_d, M'_d, D'_d)$. Set `due = newDue`.
     - **Step B (Update `suspended` in Local Calendar Space):**
       - **Case 1 (`oldSuspended` is a finite UTC timestamp with `oldSuspended < oldDue`):** Convert `oldSuspended` (UTC) into local calendar components $(Y_s, M_s, D_s, h_s, m_s, s_s)$ in the configured IANA time zone and advance $(Y_s, M_s, D_s)$ by the **same multiple $k \times \text{<count> <unit>}$** determined in Step A (applying Section 6.10.3 Step 3 for `days`/`weeks` and Step 4 month-end clamping against $D_s$ for `months`) to obtain target local date $(Y'_s, M'_s, D'_s)$.
         * **Month-End Clamping Lead-Window Preservation:** If `oldSuspended` and `oldDue` lie on different local calendar dates in the same year and month ($(Y_s, M_s) = (Y_d, M_d)$ with $D_s < D_d$), and advancing both by $k \times \text{<count> months}$ places both on the target month's last valid day $D'_s = D'_d = D_{\text{end}}$ ($D_s \ge D_{\text{end}}$ and $D_d > D_{\text{end}}$, for example `2026-01-28` or `2026-01-29` with `2026-01-31` both landing on `2026-02-28`), adjust `candidateSuspended`'s local day in that target month to:
           $$D'_s = \max(1,\; D_{\text{end}} - (D_d - D_s))$$
           (for example, $\max(1, 28 - (31 - 29)) = 26$, giving `2026-02-26` for a 2-day lead window) so `newSuspended < newDue` holds and the multi-day preparation window is not permanently collapsed to zero on subsequent completions.
         * Combine $(Y'_s, M'_s, D'_s)$ with `repeat`'s normalized `<repeat-time>` when non-midnight (`!= 00:00:00`, unless $(Y'_s, M'_s, D'_s) = (Y'_d, M'_d, D'_d)$ and $\text{<repeat-time>} \ge (h_d, m_d, s_d)$, in which case preserve $(h_s, m_s, s_s) < (h_d, m_d, s_d)$) or with `oldSuspended`'s local wall-clock time $(h_s, m_s, s_s)$ otherwise, and resolve $(Y'_s, M'_s, D'_s, h'_s, m'_s, s'_s)$ to UTC via Section 6.10.2 to obtain `candidateSuspended` (falling back to $(h_s, m_s, s_s)$ if $(Y'_s, M'_s, D'_s) = (Y'_d, M'_d, D'_d)$ and a spring-forward gap makes `candidateSuspended >= newDue`). Set `suspended = min(candidateSuspended, newDue)`.
         * **Why Local Calendar Advancement + Month-End Clamping Adjustment Avoids Both DST Drift and Lead-Window Collapse:** Advancing `oldSuspended` in local calendar space rather than subtracting raw UTC seconds ($\text{oldDue} - \text{oldSuspended}$) keeps a task due on the 15th at `18:00` local with a `suspended` start on the 10th at `08:00` local anchored at `08:00` local on the 10th across spring/autumn DST transitions, while adjusting $D'_s = \max(1, D_{\text{end}} - (D_d - D_s))$ whenever $(Y_s, M_s) = (Y_d, M_d)$ with $D_s < D_d$ and $D'_s = D'_d = D_{\text{end}}$ keeps a multi-day end-of-month preparation window open across February (`Feb 26` and `Feb 28`).
       - **Case 2 (`oldSuspended` is omitted, `forever`, or a finite UTC timestamp with `oldSuspended >= oldDue`):** Compute `candidateSuspended` on `newDue`'s local calendar date $(Y'_d, M'_d, D'_d)$ using `repeat`'s normalized local clock `<repeat-time>` (which defaults to `00:00:00` local time when omitted, resolved to UTC via Section 6.10.2), and set `suspended = min(candidateSuspended, newDue)`. This defers the next occurrence until the start of the new due date (or `<repeat-time>` on that date) and remains idempotent across all subsequent completions.
       - **Section 6.10.3 Step 7 (`> now`) Alignment:** When `due` is present, the strictly-future requirement (`> now`) in Section 6.10.3 Step 7 applies to `newDue`, whereas the resulting `suspended` (`<= newDue`) MAY be `<= now` when the previous occurrence is completed after the next occurrence's preparation window has already opened (in which case the next occurrence is immediately eligible in `Focus` under Section 5 rather than `Blocked`).
* **Restoration & Merge Semantics (Sections 6.5 & 6.7.5):**
  * Restoring a completed standard task (Section 6.5) removes `finished`, `suspended`, and `due` (while preserving `origin` unchanged).
  * Within the same occurrence (`B.completions == L.completions == R.completions` and `finished` absent), merge `due` as an independent scalar unit under Section 6.7.5.
* **Verification Cases:**
  * An open queued task with `due` next Friday and no `suspended` stays in `Focus`/`Ready`/`Planned` today.
  * Setting `due` on an unscheduled `Someday` task updates `due` and `task.modified` while keeping the task in `Someday` outside `queue`.
  * An overdue task (`due` yesterday) is manually deferred via `suspended` to tomorrow -> valid document; `Blocked` today, active tomorrow with original `due` preserved.
  * A monthly task (`repeat 1 months`) with `due` on `2026-10-15 18:00` local (CEST, UTC+2) and `suspended` on `2026-10-10 08:00` local is completed late on `2026-10-17` -> `newDue` advances by $k = 1$ month to `2026-11-15 18:00` local (CET, UTC+1) and `newSuspended` advances by $k = 1$ month to `2026-11-10 08:00` local (CET, UTC+1), preserving the exact `08:00` local wake-up clock despite the October DST transition.
  * A monthly task (`repeat 1 months`) with `due` on `2026-01-31 18:00` local and `suspended` on `2026-01-29 08:00` local is completed on `2026-01-31` -> advancing both by $k = 1$ month places both on `2026-02-28`, so `candidateSuspended`'s local day is adjusted to $\max(1, 28 - (31 - 29)) = 26$, yielding `newDue = 2026-02-28 18:00` local and `newSuspended = 2026-02-26 08:00` local (preserving `newSuspended < newDue` rather than collapsing both dates to `2026-02-28`).
  * A monthly task (`repeat 1 months`) with `due` on `2026-11-15 18:00` local and no `suspended` is completed early on `2026-11-12` -> `newDue` advances to `2026-12-15 18:00` local and `newSuspended` is set to `2026-12-15 00:00:00` local (so it stays in `Blocked` until Dec 15 begins rather than remaining in `Focus` on Nov 12).

#### 1.4.3 Topic 3: Dedicated Machine Correlation Directive (`origin "<namespace>" "<external-key>"`) & Executable URI Scheme Prohibition
* **Purpose & Strict Separation from `link` (Sections 2.8, 4.1.2 & 8):**
  * `link "<title>" "<uri>"` (`0..20`) remains strictly for user-facing clickable links that users can freely edit, reorder, or delete in the UI without breaking external tool synchronization.
  * `origin "<namespace>" "<external-key>"` (`0..1`) provides an optional, dedicated machine correlation key on a `task` block so external CLI tools, scripts, or AI agents can deterministically identify and deduplicate tasks imported from external systems (such as issue trackers, email messages, calendar events, or note vaults) across open and `Completed` states even after the user edits `name`, `note`, or `link`.
  * **Normative URI Scheme Security Rule (`InvalidUri`):** Even when `<uri>` in `link "<title>" "<uri>"` matches the syntactic scheme pattern `[a-zA-Z][a-zA-Z0-9+.-]*:`, explicitly forbid executable or script/data-bearing schemes (`javascript:`, `vbscript:`, and `data:`, matched case-insensitively on the scheme prefix) in Sections 2.8, 4.1.2, and 8, rejecting them deterministically with `InvalidUri`.
* **Syntax, Multiplicity & EBNF Grammar (Sections 3.3, 3.4 & 4.1.2):**
  * **Syntax (Depth `1` inside `task`):**
    ```text
    origin "<namespace>" "<external-key>"
    ```
  * **Multiplicity & Cross-Task Non-Uniqueness:** Optional single-valued directive (`0..1` per `task` block). List `origin` in Section 3.3 among the single-valued `task` directives (`name`, `note`, `created`, `finished`, `modified`, `completions`, `repeat`, `labels`, `blocked`, `suspended`, `due`, `origin`) so declaring `origin` more than once in the same `task` block fails deterministically with `DuplicateDirective`. Distinct `task` blocks in the same `.tdf` document MAY carry the same `(namespace, externalKey)` pair without triggering `DuplicateIdentifier` (so two offline devices or agents that independently imported the same external item with different random `<task-id>` values can still parse and merge the document cleanly before agent-level deduplication).
  * **EBNF Production (Section 3.4):** Add `origin-dir` to `directive` / `task-block` body (allowing equivalent double- or single-quoted string tokens in input per Sections 2.7.C and 6.7.9, and emitting double-quoted `"..."` strings canonically):
    ```ebnf
    origin-dir      = ws* "origin" ws+ ( quoted-string | single-string ) ws+ ( quoted-string | single-string ) ws* [ comment ] newline ;
    ```
* **Lexical, Argument & Domain Validation Rules (Sections 2.7.B, 2.7.C, 2.8, 4.1.2, 7 & 8):**
  * **Argument Count & Quoting:** Requires exactly `2` quoted string arguments (`"<namespace>"` and `"<external-key>"`, accepting either double-quoted `"..."` or single-quoted `'...'` tokens in input and emitting double-quoted `"..."` canonically):
    - If `0` arguments are provided (and no `{` follows), report `MissingDirectiveArgument`.
    - If `{` follows `origin`, report `UnknownBlockType`.
    - If `1` argument or $\ge 3$ arguments are provided, or if either argument is an unquoted bare word rather than a quoted string token, report `UnexpectedToken`.
  * **String Content & Character Bounds:**
    - Both `<namespace>` and `<external-key>` are single-line `<text>` values (identical in lexical and character rules to `task.name`, `link.<title>`, and `location.source`).
    - Unknown backslash escape sequences inside double-quoted strings (anything other than `\"`, `\\`, `\n`, `\r`, `\t`) fail at the lexical layer with `InvalidEscapeSequence` (Section 2.7.B & Section 8).
    - After unescaping, neither decoded string may contain a newline (`\n`, `0x0A`), carriage return (`\r`, `0x0D`), or horizontal tab (`\t`, `0x09`); if present (whether produced by `\n`, `\r`, `\t` escape sequences in a double-quoted string or a literal tab in a quoted string), report `UnexpectedToken` (disallowed control character in a single-line `<text>` directive, matching `task.name` and `link.<title>`).
    - If either decoded string is empty (`""`) or contains only whitespace (`0x20` ASCII spaces), report `EmptyText`.
    - Each decoded argument MUST contain between `1` and `MAX_TEXT_LENGTH` (`500`) decoded Unicode scalar values without Unicode normalization; if either exceeds `MAX_TEXT_LENGTH`, report `LimitExceeded`.
* **Canonical Formatting & Position (Sections 4.1.2 & 7.1):**
  * Emit `origin "<namespace>" "<external-key>"` at **canonical position 12** inside `task` blocks (immediately after `due` at position 11 and immediately before `link` at position 13 in the 15-position `task` directive list), with a single ASCII space (`0x20`) separating `"<namespace>"` and `"<external-key>"`.
  * Include an `origin` directive in the Section 9 (`Canonical Complete Example`) reference document.
* **Tier Evaluation, Ordinary Mutations & Task Lifecycle (Sections 5, 6.4, 6.5 & 6.6):**
  * **Non-Blocking Metadata (Section 5):** `origin` is purely passive correlation metadata and has zero effect on 6-tier derivation (`Focus`, `Ready`, `Planned`, `Blocked`, `Someday`, `Completed`), condition evaluation, or `queue` ordering.
  * **Ordinary Mutation Semantics (`Setting origin` — Section 6.6):** Setting or updating `origin` validates both `<namespace>` and `<external-key>`, advances `task.modified` once under Section 6.7.1, and preserves `queue` membership and order unchanged. Clearing `origin` removes the directive, advances `task.modified` once, and preserves `queue` membership and order unchanged.
  * **Completion & Recurrence Preservation (Section 6.4):** Completing a standard task (moving it to `Completed` with `finished`) or completing a recurring task (`repeat`, advancing `completions` and `suspended`/`due`) MUST preserve `origin` unchanged on the `task` block so external agents recognize already-completed or recurring items during subsequent sync runs.
  * **Restoration Preservation (Section 6.5):** Restoring a completed task from `Completed` removes `finished`, `suspended`, and `due`, while preserving `origin` unchanged.
* **Normalization, `Task payload` Tuple & Atomic Pair Merge (Sections 6.7.3, 6.7.4 & 6.7.5):**
  * **Normalized Value (Section 6.7.3):** Normalized `origin` is either `absent` or the 2-tuple of decoded Unicode strings `(namespace, externalKey)`. For deterministic tuple ordering (Section 6.7.4), `absent` precedes present, and present values are compared lexicographically first by `namespace` and then by `externalKey` using unsigned UTF-8 byte order.
  * **`Task payload` Tuple Order (Section 6.7.3):** Preserve the existing `0.5.1` relative ordering of `created`, `name`, `note`, `labels`, `condition`, `link`, and `Task state` by defining `Task payload` in exact component order:
    `(created, name, note, labels, condition, origin, link, Task state)`
  * **Three-Way Merge as Atomic Pair Unit (Section 6.7.5):** When merging a live `task` block across `B`, `L`, and `R`, merge `origin` (`(namespace, externalKey)` or `absent`) as **one atomic scalar unit** (never mixing `namespace` from one side with `externalKey` from the other side) using baseline `B` and complete entity winner `W` on conflict.
* **Passive Security & Diagnostic Log Redaction (`P-SECRET-HYGIENE` / `TEP-002`):**
  * `origin` arguments are strictly passive string identifiers and MUST NEVER be executed, opened as filesystem paths, or dereferenced as network URIs by a parser, evaluator, or reconciler.
  * Diagnostic logs (`TEP-002`) MUST NOT log raw `<external-key>` values (which may contain external email message subjects or vault paths); log at most `<task-id>` and `<namespace>` (or a boolean `hasOrigin` flag).

#### 1.4.5 Topic 5: Elevating Concurrent Entity References (`labels` and `condition location`) and Direct Edits Targeting Deleted Entities to `DeletionConflict`
* **Rule in Sections 6.7.5, 6.7.8 & 6.8.2:**
  * For every live or `DeletionConflict`-retained task $T$ on side $X \in \{L, R\}$ during three-way merge, define the set of newly introduced label references on side $X$ as:
    $$A_X(T) = \begin{cases} T_X.\text{labels} \setminus T_B.\text{labels} & \text{if } T \in B \\ T_X.\text{labels} & \text{if } T \notin B \text{ (newly created on side } X\text{)} \end{cases}$$
  * Analogously, for every live or `DeletionConflict`-retained entity $E \in \text{Tasks} \cup \text{Labels}$ on side $X \in \{L, R\}$ during three-way merge, let $\text{locRefs}(E)$ be the set of `<location-id>` tokens referenced across $E$'s `condition` rules, and define the set of newly introduced location references on side $X$ (evaluated on the input entities $E_L, E_R$ before `condition` unit winner selection or deletion cascades) as:
    $$A^{\text{loc}}_X(E) = \begin{cases} \text{locRefs}(E_X) \setminus \text{locRefs}(E_B) & \text{if } E \in B \\ \text{locRefs}(E_X) & \text{if } E \notin B \text{ (newly created on side } X\text{)} \end{cases}$$
  * Compute merged `T.labels` for tasks present in `B` via `added = A_L(T) union A_R(T)` and `removed = (T_B.labels minus T_L.labels) union (T_B.labels minus T_R.labels)`, and retain $A_X(T)$ for tasks newly created on side $X$.
  * Never silently strip a label ID $l \in A_L(T) \cup A_R(T)$ or a location ID $\text{loc} \in A^{\text{loc}}_L(E) \cup A^{\text{loc}}_R(E)$ merely because the opposing side contains a deletion record for `label` $l$ or `location` $\text{loc}$ in `deleted`.
  * **Normative `DeletionConflict` Classification & Live Entity Preservation (Both Direct Entity Edits and Newly Introduced References):** Classify `label` $l$ or `location` $\text{loc}$ as a **`DeletionConflict`** under Section 6.8.2 — retaining the live `label` or `location` block alongside the opposing side's deletion record — whenever **either** of the following holds:
    1. **Direct Entity Payload Edit vs. Deletion:** The live `label` $l$ or `location` $\text{loc}$ block's own normalized payload changed relative to `B` on one side while the opposing side contains a deletion record in `deleted` (or no proven baseline `B` is available).
    2. **Newly Introduced Reference vs. Deletion:** Any live or `DeletionConflict`-retained task $T$ on side $X \in \{L, R\}$ introduces a label ID $l \in A_X(T)$ while `label` $l$ has a deletion record in `deleted` on the opposing side, or any live or `DeletionConflict`-retained `task` or `label` $E$ on side $X \in \{L, R\}$ introduces a location ID $\text{loc} \in A^{\text{loc}}_X(E)$ while `location` $\text{loc}$ has a deletion record in `deleted` on the opposing side (evaluated before `condition` winner selection or deletion cascades, even when that `label` or `location`'s own payload was unchanged relative to `B`).
    - **User/Caller Chooses `Delete`:** Confirms deletion of `label` $l$ or `location` $\text{loc}$ with `decisionRevision`, removes $l$ from all tasks (applying the `scoped` queue-eviction rule from Topic 6 if applicable) or removes $\text{loc}$ from all `label` and `task` `condition` rules in label-before-task order (applying the task `location any` override-preservation rule from Topic 12 if applicable), advances `modified` on all affected entities, and publishes the valid result.
    - **User/Caller Chooses `Undelete`:** Restores the retained live `label` $l$ or `location` $\text{loc}$ block with `modified = decisionRevision`, removes its record from `deleted`, increments `deleted.generation` once, and preserves all references on tasks and labels.

#### 1.4.6 Topic 6: View-Scoped Labels (`label <label-id> [scoped] {`), Global-View Flood Protection, and Context-Relative Downgrades
* **Syntax, Payload Tuple Order & Merge Granularity (Sections 4.2, 6.7.3 & 6.7.5):**
  * Permit an optional `scoped` bare-word flag in the `label` block header:
    ```text
    label <label-id> [scoped] {
        name "<display_name>"
    }
    ```
    Any unknown or extra header flag on `label` produces `InvalidBlockHeader`.
  * Define the `Label payload` tuple in Section 6.7.3 in exact component order `(scoped, name, note, color, condition)` (where an omitted `scoped` flag is `false`, preceding `true`), and merge `scoped` as an **independent boolean scalar unit** alongside `name`, `note`, `color`, and `condition` when a live `label` block is merged across `B`, `L`, and `R` (Section 6.7.5).
* **Global-View Pre-Filtering Rule (Section 5.1):**
  Let $L(T)$ be the set of declared labels referenced in task $T$'s `labels` directive, and let $\text{isScoped}(l)$ be `true` when label $l$ has the `scoped` header flag:
  * **Active Label Filter Selected (`activeLabelId = l*`):** Unchanged. Every task $T$ with $l^* \in L(T)$ enters Sections 5.2 through 5.5.
  * **No Label Filter Selected (Global View):** Task $T$ is **restricted from the global view** (excluded in Section 5.1) if and only if $L(T)$ is non-empty and **every** assigned label in $L(T)$ is `scoped`:
    $$\text{isRestrictedFromGlobalView}(T) \iff L(T) \neq \varnothing \;\land\; \forall l \in L(T),\; \text{isScoped}(l)$$
    Tasks with $L(T) = \varnothing$ or with at least one regular (non-`scoped`) label ($\exists l \in L(T),\; \neg\text{isScoped}(l)$) enter the global view normally.
  * **Global Search & Prerequisite Resolution (`blocked`):** Search always inspects all tasks in the document. Prerequisite evaluation (`blocked` in Sections 5.4 and 6.9.2) always resolves across the complete document regardless of `scoped`.
* **Global-View Condition Evaluation for Mixed-Label Tasks (Section 4.4.3, formerly 4.3.3 Rule 4):**
  * When a task $T$ has at least one non-`scoped` label ($\exists l \in L(T),\; \neg\text{isScoped}(l)$) alongside one or more `scoped` labels, $T$ is evaluated in the **global view** strictly as if it had **no `scoped` labels**:
    $$L_{\text{global}}(T) = \{\, l \in L(T) \mid \neg\text{isScoped}(l) \,\}$$
  * Only the non-`scoped` labels $L_{\text{global}}(T)$ form candidate condition contexts (`OR` across $l \in L_{\text{global}}(T)$) in the global view.
* **Global-View Flood Protection on `scoped` Label Deletion (Sections 6.7.8, 6.8.1 & 6.8.2):**
  * Whenever one or more `scoped` labels are removed from a live task $T$ due to label deletion — whether via an explicit label deletion command (Section 6.8.1), an explicit `Delete` conflict resolution (Section 6.8.2), or non-conflicting label deletion during three-way merge reconciliation (Section 6.7.8):
    - Let $L_{\text{before}}(T)$ be $T$'s assigned label set immediately prior to removing labels tombstoned in `deleted` (during three-way merge, $L_{\text{before}}(T)$ is $T$'s merged label set computed without removals of labels that are tombstoned in the merged `deleted` block, so labels already stripped from $T$ on the deleting side as part of the label deletion are included in $L_{\text{before}}(T)$, with $\text{isScoped}(l)$ taken from the merged live `label` block for surviving labels and from the surviving side/`B` for tombstoned labels), and let $L_{\text{after}}(T) = L_{\text{before}}(T) \setminus \text{DeletedLabels}$ be $T$'s label set after removing tombstoned labels.
    - If $T$ was restricted from the global view prior to removing the deleted label(s) ($L_{\text{before}}(T) \neq \varnothing \land \forall l \in L_{\text{before}}(T),\; \text{isScoped}(l)$), and removing the deleted label(s) leaves $T$ with **zero labels** ($L_{\text{after}}(T) = \varnothing$), and $T$ is listed in `queue` (or in the merged `queue` during Section 6.11.2), **remove $T$'s task ID from `queue` and strip `priority` if present in the same atomic transaction while preserving `suspended`** (so unscheduled tasks without active deferrals enter `Someday` under Section 5.3, while deferred or recurring tasks keep their `suspended` schedule in `Blocked` -> `Someday` under Sections 5.3 and 5.4).
    - For explicit deletion mutations and conflict resolutions (Sections 6.8.1 & 6.8.2), advance `T.modified` and `queue.modified` using the mutation rule (`max(now, previous + 1 second)`). During three-way merge reconciliation (Sections 6.7.6, 6.7.8 & 6.11.2), compute `T.modified` and `queue.modified` strictly via the deterministic merge revision rules without reading the current clock (reusing the greatest existing version's `modified` timestamp if its payload/list already matches the final post-cascade result, or setting `modified = max(B, L, R) + 1 second` otherwise).
    - This prevents a deleted `scoped` list (including tasks concurrently scheduled into `queue` on one device while their `scoped` label was deleted on another device) from flooding the global `Focus` and `Ready` tiers as unlabeled tasks.
    - If $T$ also carried a non-`scoped` label ($L_{\text{after}}(T)$ contains a regular label, so $T$ was already in the global view) or still retains another live `scoped` label ($L_{\text{after}}(T) \neq \varnothing$), keep $T$'s entry in `queue`.
* **Active-Filter-Relative Step-Down Downgrade Anchor (Section 6.3):**
  * Clarify in Section 6.3 that when downgrading an active task $T$ from `Focus` to `Ready`, $T$'s `priority` flag and target position in `queue` are determined **relative to the Section 5.5 priority-partitioned executable tasks matching the currently active filter context (`activeLabelId`)**:
    - Let $E_{\text{ctx}}$ be the Section 5.5 Step 2 priority-partitioned ordered sequence of executable tasks (`[...focus, ...ready, ...planned]` excluding $T$ itself, i.e., `priority` tasks in `queue` order followed by non-`priority` tasks in `queue` order) that pass Section 5.1 through Section 5.4 for the active `activeLabelId` (`null` for global view, where `scoped`-only tasks are excluded; or `l*` for a filtered label view).
    - **If $|E_{\text{ctx}}| \ge 7$:** Strip `priority` if present (unless the 7th task in $E_{\text{ctx}}$ carries `priority`, in which case preserve `priority` to match the slot-8 anchor as in Section 6.3) and move $T$ in `queue` immediately after the **7th task in $E_{\text{ctx}}$** so $T$ occupies the 8th executable slot (the last slot of `Ready`) in the active filter context.
    - **If $1 \le |E_{\text{ctx}}| < 7$:** Strip `priority` if present and move $T$ in `queue` immediately after the **last task in $E_{\text{ctx}}$** (rather than appending $T$ to the very end of the global `queue` behind unrelated tasks from other labels).
    - **If $|E_{\text{ctx}}| = 0$:** Strip `priority` if present and keep $T$'s position in `queue` unchanged (applying the No-Op revision protection rule from Section 6.3 when neither `priority` nor `queue` order changes).

#### 1.4.7 Topics 7 & 8: Fine-Grained Same-Occurrence Merging, Key-Value Map Merge for `blocked`, Step-Wise `subtasks` Merge, Pre-Merge Tombstone Stripping on `condition`, and Independent `scoped` Flag Merge
* **Label `scoped` Flag Merge (Sections 6.7.3 & 6.7.5):**
  * When merging a live `label` block across `B`, `L`, and `R`, merge its `scoped` boolean header flag as an independent scalar unit alongside `name`, `note`, `color`, and `condition` (ordered as `(scoped, name, note, color, condition)` in the `Label payload` tuple of Section 6.7.3).
* **Pre-Merge Tombstone Stripping and Commutative Group-Wise `condition` Merge (Sections 6.7.3, 6.7.5, 6.7.7 & 6.7.8):**
  * During three-way merge of a `label` or `task` block, before comparing `B.condition`, `L.condition`, and `R.condition` as a scalar unit (or per rule group) in Section 6.7.5, any `<location-id>` that is non-conflictingly tombstoned in the merged `deleted` block (i.e., not in `DeletionConflict`) MUST be stripped from `B.condition`, `L.condition`, and `R.condition` (removing an emptied `location` rule in this pre-comparison projection, and projecting a task's cascade-inserted `location any` back to the empty `locationGroup` when `B.locationGroup` contained only locations tombstoned on that side). This ensures that when side `R` deletes a `location` (cascading `<location-id>` out of `T_R.condition`) while side `L` concurrently edits `day` or `time` in `T_L.condition`, the normalized `location` change on `R` matches the pre-stripped baseline `B` (`R.condition == B.condition` on the location component), allowing `L`'s `day`/`time` edit to merge cleanly without a false `condition` conflict, after which the post-merge `label`-before-`task` `location any` inheritance-trap check (Section 1.4.8) is applied.
  * If any of projected `B.condition`, `L.condition`, or `R.condition` sets `globalAny == true` (`condition any`), merge the complete `condition` model as one atomic scalar unit using projected `B` and complete entity winner `W`. Otherwise (`globalAny == false` in all three), merge `dayGroup`, `timeGroup`, and `locationGroup` as three independent rule-group units using projected `B`, complete entity winner `W`, and opposing side `Loser`:
    - For `dayGroup` and `timeGroup`: apply the standard three-way scalar rule using `W` on conflict.
    - For `locationGroup` (preserving strict commutativity `merge(B, L, R) == merge(B, R, L)`): if `L.locationGroup == R.locationGroup`, keep `L.locationGroup`; else if `L.locationGroup == B.locationGroup`, keep `R.locationGroup`; else if `R.locationGroup == B.locationGroup`, keep `L.locationGroup`; else if `resetAny == true` (`location any`) in any of `B.locationGroup`, `L.locationGroup`, or `R.locationGroup`, keep `W.locationGroup`; else (both `L` and `R` modified their `<location-id>` lists with `resetAny == false`), start from `W.locationGroup`'s ordered `<location-id>` list, remove any `<location-id>` in `B minus Loser`, and append any `<location-id>` in `Loser minus B` not already present in `Loser`'s declaration order. Validate the merged entity under Section 6.7.7 against `MAX_ARGS_PER_STMT = 64` and `MAX_LOCATION_REFS_PER_ENTITY = 63` (`LimitExceeded` if exceeded).
* **Two-Level Task Occurrence Merge Rule (Sections 6.7.3 & 6.7.5):**
  * Define the `Task state` tuple in Section 6.7.3 in exact component order `(completions, priority, finished, suspended, due, repeat, blocked, subtasks)`.
  1. **Cross-Occurrence or Completion-State Transition (`completions` differs among `B`, `L`, `R`, or `finished` is present in at least one of `B`, `L`, `R`):**
     - Retain the atomic rule: copy the complete occurrence state (`completions`, `priority`, `finished`, `suspended`, `due`, `repeat`, `blocked`, `subtasks`) from the complete entity winner `W` (where the greater `completions` counter wins under Section 6.7.4).
  2. **Same-Occurrence Concurrent Edit (`B.completions == L.completions == R.completions` and `finished` is omitted in `B`, `L`, and `R`):**
     - Merge each operational unit independently using the three-way baseline `B` and complete entity winner `W`:
       - `priority`: Independent boolean scalar unit.
       - `suspended`: Independent deferral scalar unit.
       - `due`: Independent timestamp scalar unit.
       - `repeat`: Independent recurrence rule scalar unit.
       - `blocked`: **Key-Value Map Merge by `targetId`:**
         Using the normalized prerequisite maps $M_B, M_L, M_R : \text{TaskId} \rightharpoonup \mathbb{N}^+$ from Section 6.7.3 (where each entry maps a prerequisite `targetId` to its `requiredCompletion`, or `absent` if not referenced), resolve each `targetId` in $\text{dom}(M_B) \cup \text{dom}(M_L) \cup \text{dom}(M_R)$ independently:
         1. If $M_L(\text{id}) = M_R(\text{id})$, keep $M_L(\text{id})$.
         2. Else if $M_L(\text{id}) = M_B(\text{id})$, keep $M_R(\text{id})$ (incorporating independent prerequisite additions, removals, or requirement updates from `R`).
         3. Else if $M_R(\text{id}) = M_B(\text{id})$, keep $M_L(\text{id})$ (incorporating independent prerequisite additions, removals, or requirement updates from `L`).
         4. Else (both `L` and `R` changed `targetId` to different states), keep $M_W(\text{id})$.
         Validate the resulting dependency graph across the complete merged document for `CircularDependency` and `MAX_ARGS_PER_STMT = 64` (Section 6.7.7).
       - `subtasks` (**Step-Wise Boolean Merge on Matching Step Texts**):
         - When `B.subtasks`, `L.subtasks`, and `R.subtasks` are all present and have the exact same ordered sequence of decoded step `<text>` strings $[s_1, \dots, s_m]$, merge the `auto-finish` header flag and each step $i$'s `<bool>` completion flag ($i \in 1..m$) independently via the three-way scalar rule.
         - Otherwise (if `subtasks` was added, removed, reordered, or had step `<text>` edited on either side), merge the complete `subtasks` block as one atomic unit via the three-way rule using `W` on conflict.
         - Preserve the Section 6.7.5 invariant: synchronization MUST NOT independently trigger task completion or recurrence even if all merged steps become `true` on a `subtasks auto-finish` block.

#### 1.4.8 Topic 12: First-Class Reusable `location <location-id> { ... }` Entities and ID-Referenced `condition location` Rules
* **Root Block `location <location-id> { ... }` (New Section 4.3, Renumbering Sections 4.3–4.5 to 4.4–4.6):**
  * Introduce a root-level `location` entity block at depth `0` (permitting directives only at depth `1` and forbidding nested blocks with `UnknownBlockType`, analogous to `deleted` and `queue`), modeled alongside `label` and bounded by `MAX_LOCATIONS = 200` per document (`LimitExceeded` on the 201st `location` block, while also counting toward `MAX_BLOCKS_PER_DOC = 4_096`):
    ```text
    location <location-id> {
        name        "<display_name>"
        note        "<optional_description>"
        source      "<optional_address_or_code>"
        coordinates <lat> <lon>
        radius      <meters>
        modified    <YYYY-MM-DD> [<HH:MM[:SS]>]
    }
    ```
  * **Header & Identity Namespace (Sections 2.8, 2.9, 3.4 & 4.3):**
    - `<location-id>` is a required unquoted 10-character Base62 identifier (`<6xBase62Random><4xBase62Time>`, `[0-9A-Za-z]{10}`, generated under Section 2.9). Missing ID or extra header argument produces `InvalidBlockHeader`; a quoted or noncanonical ID produces `InvalidIdentifier`.
    - `location` uses a dedicated identity namespace separate from `task` and `label`. Within the `location` namespace, duplicate live `location` blocks, duplicate `deleted` `location` records, or a live `location` block sharing an ID with a `deleted` `location` record MUST report `DuplicateIdentifier`.
  * **Single-Valued Directives, Numeric/Precision Bounds & Passive-Metadata Security (Sections 2.8, 3.3, 4.3, 6.7.3 & 7):**
    All six directives inside `location` are single-valued (`DuplicateDirective` on repetition; `UnknownDirective` on any other directive; `UnknownBlockType` on any nested block; `MissingDirectiveArgument` on `0` arguments without `{`) and emitted in this exact canonical order (Section 7.1):
    1. `name "<text>"` (**Required**, `1`): Human-readable display title of the place (`1..MAX_TEXT_LENGTH` decoded Unicode scalar values, not blank/whitespace-only after unescaping; `EmptyText` if blank; `InvalidEscapeSequence` on unknown backslash escapes; `UnexpectedToken` if the decoded string contains `\n`, `\r`, or `\t`).
    2. `note "<text>"` (**Optional**, `0..1`): Descriptive note for the location (`1..MAX_NOTE_LENGTH` decoded Unicode scalar values, not blank/whitespace-only after unescaping; `EmptyText` if blank; `\n`, `\r`, `\t` permitted via escape sequences, identical to `label.note` and `task.note`).
    3. `source "<text>"` (**Optional**, `0..1`): Human- or tool-readable address or location code, such as a street address (`"Bahnhofstraße 1, 99084 Erfurt"`), an Open Location Code / Google Plus Code (`"9F2PXXH7+F4"`), or a What3words code (`"///index.home.raft"`) (`1..MAX_TEXT_LENGTH` decoded Unicode scalar values, not blank/whitespace-only after unescaping; `EmptyText` if blank; `InvalidEscapeSequence` on unknown backslash escapes; `UnexpectedToken` if the decoded string contains `\n`, `\r`, or `\t`).
       - **Normative SSRF & Passive-Metadata Security Rule (Section 4.3):** `location.source` is strictly passive textual metadata during parsing, migration, synchronization, and 6-tier evaluation (Section 5). A conforming parser, migrator, reconciler, or tier evaluator MUST NEVER automatically invoke external geocoding services, network APIs (such as Nominatim, Google Maps, or What3words), or filesystem/UNC paths (`\\server\share`) when processing `source`. If a consuming application offers an explicit user action to open `source` in an external map viewer, it MUST pass `source` as a URL-encoded query parameter to a safe map URI template (`https:` or `geo:`) rather than launching `source` as an unvalidated raw URI or OS command.
    4. `coordinates <lat> <lon>` (**Required**, `1`): Two unquoted finite ASCII decimal `<number>` tokens (`-?[0-9]+(\.[0-9]+)?`; a `<number>` token exceeding `MAX_NUMBER_LENGTH = 24` ASCII characters fails with `LimitExceeded` under Section 7, while `NaN`, `Infinity`, `-Infinity`, leading `+`, scientific notation `1e5` / `1E-3`, or other malformed literals fail with `InvalidNumber`): `<lat>` in `[-90.0, 90.0]` and `<lon>` in `[-180.0, 180.0]` in WGS-84 decimal degrees (`InvalidNumber` if out of range; `MissingDirectiveArgument` if `0` arguments; `UnexpectedToken` if quoted or argument count is `1` or $\ge 3$).
       - **Coordinate Precision Cap (`P-SECRET-HYGIENE`):** After stripping trailing fractional zeros under Section 6.7.3, `<lat>` and `<lon>` in native `tdf 0.6.0` documents MUST have at most **6 fractional decimal digits** ($\approx 11\text{ cm}$ resolution; inputs with $> 6$ non-zero fractional digits produce `InvalidNumber`), preventing raw hardware sensor-float fingerprinting in shared `.tdf` files.
       - **Canonical Formatting (Section 7.1):** Canonical serialization emits `<lat>` and `<lon>` using the Section 6.7.3 normalized decimal representation (`-0.0` normalized to `0`, redundant leading integer zeros and trailing fractional zeros removed).
    5. `radius <meters>` (**Required**, `1`): One unquoted finite ASCII decimal `<number>` token (`LimitExceeded` if token length $> \text{MAX\_NUMBER\_LENGTH} = 24$, at most **2 fractional decimal digits** after stripping trailing zeros) satisfying $0 < \text{meters} \le \text{MAX\_LOCATION\_RADIUS}$ (`MAX_LOCATION_RADIUS = 100_000` meters / $100\text{ km}$; `InvalidNumber` if $\le 0$, $> 2$ non-zero fractional digits, or malformed; `LimitExceeded` if $> \text{MAX\_LOCATION\_RADIUS}$; `MissingDirectiveArgument` if `0` arguments; `UnexpectedToken` if quoted or argument count $\ge 2$). Canonical serialization emits `<meters>` using the Section 6.7.3 normalized decimal representation.
    6. `modified <YYYY-MM-DD> [<HH:MM[:SS]>]` (**Optional**, `0..1`): UTC entity revision timestamp (`InvalidTimestamp` if invalid; effective value when omitted is `1970-01-01 00:00:00` UTC under Section 6.7.1, identical to `label.modified`).
    - Omitting `name`, `coordinates`, or `radius` produces `MissingRequiredDirective`.
    - **Diagnostic Log Redaction (`P-SECRET-HYGIENE` / `TEP-002`):** Diagnostic logs MUST record only the opaque 10-character Base62 `<location-id>` and MUST NEVER log `location.name`, `location.note`, `location.source`, or `location.coordinates`.
* **ID-Referenced `location` Condition Rules, Canonical Coalescing & Reference Bounds (Section 4.4, formerly 4.3):**

    - Inside `condition { ... }` (depth `2`): `location <loc-1> [<loc-2> ...]`

    - Every `<loc-i>` token (`1..N`) in a non-reset `location` condition rule MUST be an unquoted 10-character Base62 `<location-id>` (`InvalidIdentifier` if quoted or malformed).

  * **Rule Counting, Per-Entity `<location-id>` Cap (`MAX_LOCATION_REFS_PER_ENTITY = 63`) & Canonical Coalescing (Sections 4.4.1, 6.7.3, 7 & 7.1):**

    - As in `0.5.1`, if the evaluation environment provides no current GPS coordinates, `location` rules evaluate to `true`.

  * **Payload Tuple & Coupled `(coordinates, source)` Merge Unit (Sections 6.7.3 & 6.7.5):**

      1. `name`: Independent scalar unit.
      2. `note`: Independent scalar unit.
      3. `(coordinates, source)`: **Coupled geographic reference unit** combining `coordinates` `(normalizedLat, normalizedLon)` and optional `source` `"<address_or_code>"`. Merging `(coordinates, source)` as one atomic unit guarantees that a concurrent address typo fix on old coordinates (`R`) and a relocation to new coordinates + new address (`L`) never produce a mismatched hybrid of old `source` and new `coordinates`.

  * **Deletion Records, External Deletion Synthesis, 30-Day Cleanup, History-Expiry Recovery, Pre-Merge Tombstone Stripping on `condition`, Label-Before-Task Cascade Order & Override-Preserving Cascade (Sections 4.5, 6.7.5, 6.7.8, 6.8.1, 6.8.2, 6.8.3 & 6.8.4):**

This guarantees that when side `R` deletes a `location` (cascading `<location-id>` out of `T_R.condition`) while side `L` concurrently edits `day` or `time` in `T_L.condition`, the normalized `location` change on `R` matches the pre-stripped baseline `B`, allowing `L`'s `day`/`time` edit to merge cleanly without a false `condition` conflict, after which the post-merge `label`-before-`task` `location any` inheritance-trap check is applied.

      1. **First on all `label` blocks:** Remove every tombstoned `<location-id>` from each live `label`'s `location` condition rule; if zero `<location-id>` tokens remain on a `label`, remove its `location` rule (and omit `condition` if zero rules remain across all groups), advancing `label.modified`.

#### 1.4.9 Topics 10 & 11: Prerequisite Expiry Hygiene on 30-Day Tombstone Retirement and Time Zone Context
* **Topic 10 (Prerequisite Reference Hygiene — Section 6.8.3):**
  * Missing target `<task-id>` tokens in `blocked` MUST NOT be pruned during parsing, loading, or ordinary mutations, preserving hand-edited forward references (Section 10.4.1) and out-of-order sync arrivals.
  * **Normative 30-Day Tombstone Expiry Cleanup Rule (`0.6.0` — Section 6.8.3):** During a guarded 30-day deletion record cleanup transaction (Section 6.8.3), whenever a task deletion record `task <id> <ts> [<checkpoint>]` is being retired after $> 30$ days (`now - ts > 2_592_000` seconds), any `blocked` reference `<id>[:<req>]` targeting that expiring `<id>` on any live task MUST be removed in the same guarded cleanup transaction (omitting `blocked` if no dependencies remain and advancing each affected live task's `modified` timestamp under Section 6.7.1) regardless of `<checkpoint>`. Because any `<id>` present in `deleted` is a confirmed deleted task (never a forward reference) and can never be reused after 30-day expiry (Sections 6.8.1 and 6.8.4), retiring `<id>[:<req>]` unconditionally upon 30-day tombstone expiry cleans up both completed prerequisites (`checkpoint >= req`) and deleted uncompleted prerequisites (`checkpoint = 0`) while keeping forward references (which have no record in `deleted`) completely untouched.
* **Topic 11 (Time Zone Hint):**
  * Deferred / kept out of `task`, `label`, and `location` blocks to preserve file compactness. Headless tools continue to pass an explicit IANA zone parameter (or read an optional workspace-level setting outside entity blocks).

### 1.5 Alternatives
1. **Use Physical `.tdf.lock` Files Inside the Workspace Directory (Topic 1 Alternative):**
   * *Rejected:* Cloud synchronization clients (Nextcloud, OneDrive, Syncthing) synchronize `.tdf.lock` files across devices, causing ghost locks if a process exits or sync lags. A SHA-256 `sourceDigest` CAS-merge loop (`MAX_CAS_RETRIES = 3`) with CSPRNG `O_CREAT | O_EXCL` dot-prefixed temp-file swap and unconditional error `unlink` provides lock-free cross-device safety.
2. **Implicit Priority Boost for Approaching `due` Dates, Raw UTC-Second Lead-Time Subtraction, or Unadjusted Month-End Clamping of `suspended` (Topic 2 Alternatives):**
   * *Rejected:* Implicitly promoting tasks based on `due` undermines the explicit pull-system guarantees of `queue` and `priority`. Subtracting raw UTC seconds ($\text{oldDue} - \text{oldSuspended}$) shifts local wake-up times by $\pm 1$ hour across DST transitions, while clamping both `2026-01-29` and `2026-01-31` to `2026-02-28` in February without adjustment permanently collapses the multi-day preparation window into Case 2 (`oldSuspended >= oldDue`). Advancing `oldDue` and `oldSuspended` by $k \ge 1$ intervals in local calendar space and adjusting `candidateSuspended`'s local day to $\max(1, D_{\text{end}} - (D_d - D_s))$ whenever different local dates clamp to the same month-end day $D_{\text{end}}$ preserves both the exact local wake-up clock across DST transitions and the multi-day lead window across shorter months without adding extra keywords to `repeat`.
3. **Overload `link "<title>" "<uri>"` with a Third External-Key Parameter (Topic 3 Alternative):**
   * *Rejected:* Mixing visible user links with internal agent correlation keys causes deduplication breakage whenever a user edits or deletes a link in the UI; a dedicated `origin "<namespace>" "<external-key>"` (`0..1`) directive cleanly separates passive machine correlation from user-facing `link` items.
4. **Abort Merge with `UnknownLabelReference` or `UnknownLocationReference` on Concurrent Reference to a Deleted Entity (Topic 5 Alternative):**
   * *Rejected for `0.6.0`:* Classifying the collision as `DeletionConflict` (Section 6.8.2) reuses the existing `Delete` vs. `Undelete` resolution mechanism instead of stranding the user with a low-level schema error.
5. **Append Inline Trailing Note and Address Strings Directly to `condition location <lat> <lon> <radius>` or Merge `source` Independently of `coordinates` (Topic 12 Alternatives):**
   * *Rejected:* Keeping locations inline inside `condition` forces users to duplicate raw coordinates, radii, notes, and street addresses / Plus Codes / What3words codes across every task and label that shares the same physical place. Likewise, merging `source` and `coordinates` as separate scalars can pair an old address with relocated coordinates; coupling `(coordinates, source)` as a single geographic reference unit inside a root `location <location-id> { ... }` block prevents address/coordinate divergence.
